🖼 The Word Dictionary (click any word)

One real-life analogy per term. That is all you need to follow the whole page.
🧑‍🍳 AI AgentA restaurant waiter. You say what you want; he walks to the kitchen, checks the chef, brings your food. An agent uses “tools” to finish your request.
🍳 ToolThe waiter’s helpers: the menu (look up), the kitchen (do work), the phone (call outside). The things an agent is allowed to use.
💰 Reliable agentA waiter who, when the kitchen says “no fish,” doesn’t freeze — he checks again, offers chicken, tells the manager. Keeps working when things go wrong.
⏱️ TimeoutCalling a friend: you don’t wait forever. After ~10s you hang up and try again. “Stop waiting, move on.”
📞 Retry (backoff)Calling back, but not 100 times in a second. You wait longer each time (2s, 4s, 8s) so you don’t spam.
🔃 IdempotencyPressing the lift button twice doesn’t call two lifts. A “already did this” tag so a retry doesn’t charge the card twice.
📚 RAGA librarian. Instead of memorising every book he finds the 3–5 most useful ones, reads them, answers only from those.
🪄 Embedding / Vector DBA magic shelf where books sit by MEANING not title. “Fix a bike” lands next to “repairing wheels.” Finds similar ideas fast.
🃏 ChunkingCutting a thick textbook into recipe cards so you grab just the card you need.
✅ Recall@kDid the librarian bring the RIGHT books? Asked for cake and got 5 muffin books — bad recall.
🤬 Faithful vs HallucinationFaithful = “the book says X.” Hallucination = inventing “and also Y” that no book ever said.
📝️ EvaluationA test with 100 questions you already know the answers to, checked BEFORE real customers use it.
💍 OrchestrationA wedding planner coordinating caterer, florist, photographer and band so everything arrives together.
🎮 State / checkpointA video-game save point. Crashed at level 3? Reload the save — don’t replay the whole game.
✈️ Saga / compensationBooked a flight + hotel; hotel sold out. Don’t strand them — cancel the flight too. “Undo” = compensation.
✍️ Human-in-the-loopBig purchases need a manager’s signature. The robot works but pauses and asks a human before the risky step.
🚘 Latency / p95How fast the waiter brings food. p95 = “95 of 100 orders arrived within this time” — the almost-always-fast number.
💵 CostThe bill. Cheap chef for toast, fancy chef only for the wedding cake.
🚗 GuardrailsSeatbelts + airbags. Check what the customer said (guard in) and the AI’s answer is safe (guard out).
🛯 PII maskingBlurring the home address on a package before a stranger sees it.
🔑 RBACOnly the manager has the safe key. Different people can do different things.
🐦 Canary deployTrying a new recipe on 5 customers first, before changing the whole menu.

Q1 • Building an agent vs making it reliable

Interviewer asks: Your refund tool returns {amount:null}. Does the workflow recover? Are retries and timeouts handled? Walk me through.
🧈 Explain like I’m 5: A basic waiter hears “no fish” and freezes. A reliable waiter: he asks again (retry), doesn’t wait all day (timeout), offers chicken instead (fallback), and remembers the table so a restart doesn’t lose the order (save point). That’s the graph on the right.
🌍 Real world: Gartner (2024) said ~30% of AI projects get abandoned after the demo — usually because only the happy path worked. Reliability is what separates a demo from a product.

🖼️ Connected diagram: state flows, diamonds decide, one arrow loops back

Read it like a subway map: follow the arrows. Diamonds ask a yes/no. The amber loop is the retry. The teal and coral arrows are the two ways out.

🐍 The same graph as code (LangGraph)

class S(TypedDict):
    order: dict; answer: str | None; tries: int

def call_tool(s):  return {"order": fake_api(s["order"])}   # may fail
def route(s):                                   # the diamond
    try:   Order(**s["order"]); return "answer"
    except ValidationError:
        return "retry" if s["tries"] < 3 else "fallback"

g = StateGraph(S)
g.add_node("call_tool", call_tool)
g.add_node("answer",    answer_node)
g.add_node("fallback",  fallback_node)
g.add_edge(START, "call_tool")
# add_conditional_edges = the diamond + its labelled arrows
g.add_conditional_edges("call_tool", route, {
    "answer":   "answer",      # ✓ valid
    "retry":    "call_tool",   # ← the amber loop (waits 2/4/8s)
    "fallback": "fallback",    # ✗ after retries exhausted
})
g.add_edge("answer",   END)
g.add_edge("fallback", END)
app = g.compile(checkpointer=SqliteSaver)  # save-point per step
Every add_node = a box. Every add_edge = an arrow. add_conditional_edges = a diamond. checkpointer = the save point.
🎮 Playground — run the graph: click a few times. Sometimes the tool flakes (amber loop), sometimes it passes straight through.
💬 Say it in the interview: “I model it as a state graph: every tool call has a timeout and a few retries that wait longer each time, a Pydantic guard acts as the routing diamond, and the retry edge loops back to the same node. If retries exhaust I route to a fallback node, and a checkpointer saves state at every step so a crash resumes instead of restarting.”

Q2 • Building RAG vs evaluating RAG

Interviewer asks: How would you measure retrieval quality? Without evaluation you’re just hoping it works.
🧈 Explain like I’m 5: A librarian answers from books. Before trusting him with real customers, test him with questions you already know. Two things: did he bring the right books (recall)? Did he tell you only what books say (faithful) or make it up (hallucination)? That test = evaluation.
🌍 Real world: Feb 2024 — Air Canada’s chatbot invented a refund policy; a tribunal made the airline honour it. Hallucination isn’t a typo, it has a legal cost. That’s why we measure faithfulness.

🖼️ Connected diagram: retrieve → rerank → generate → faithfulness diamond

Straight arrows = pipeline steps. The amber diamond = the faithfulness gate. The red arrow looping back = “score too low, fix the retrieval and try again.”

🐍 Score it like code (RAGAS)

# golden set: 100 questions with known answers
from ragas import evaluate
from ragas.metrics import faithfulness, recall, precision

res = evaluate(golden_set, metrics=[
    recall,         # did retrieve bring the right cards?
    precision,      # were the cards actually on-topic?
    faithfulness,   # did the answer stay inside the cards?
])
# the diamond in the diagram = this gate:
if res["faithfulness"] < 0.85:
    fix_chunks_or_rerank()      # ← red loop back
    rerun()
else:
    deploy()                    # → answer + cite + END

# recall 0.68 → 0.86 when chunks 800→400 tokens + rerank
Two halves, two scores: retrieval (recall/precision) and generation (faithfulness). Never average them into one number.

💬 Say it in the interview: “I keep a golden test set and score the two halves separately — recall/precision for retrieval, faithfulness for generation — and I gate deploys on faithfulness above 0.85, re-running nightly so a bad chunk or stale price is caught automatically.”

Q3 • Using tools vs orchestrating a workflow

Interviewer asks: The agent must fetch data, call an API, validate, update a system. What if the API fails halfway? Show state, error recovery, control.
🧈 Explain like I’m 5: A travel agent books your flight, then tries your hotel — sold out. A careless agent leaves you with a flight to nowhere. A smart one undoes the flight, tells you, offers options. That “undo” = compensation. A wedding planner keeps a checklist (state) so a hiccup isn’t a fresh start.
🌍 Real world: In 2012 a bug at Knight Capital ran bad trades and lost $440M in 45 minutes. FDE lesson: risky steps need an undo plan, a checkpoint, and human approval — not hope.

🖼️ Connected diagram: happy path (top) vs compensation path (bottom)

Top row = the happy path. The red branch is the compensation: book-hotel failed, so we undo the flight, notify, and still reach a safe END. Nobody is stranded.

🐍 Same graph as code (saga + state)

state = {"step": "start", "pay": None}

try:
    state["pay"] = book_flight()     # → node 1
    book_hotel(state)                # → node 2 (may fail)
    confirm(state)
except HotelUnavailable:
    compensate(state)                # ← red branch

def compensate(state):
    refund(state["pay"])             # undo the successful step
    notify_user("hotel full + 2 options")
    # each step has a matching UNDO W a saga

# LangGraph version: conditional edge on the diamond
g.add_conditional_edges("book_hotel", route, {
    "ok":  "confirm",
    "fail": "refund",     # ← compensation node
})
g.add_edge("refund", "notify"); g.add_edge("refund", END)
Two rules: keep state (you always know what’s done) and give every risky step a matching undo. add_conditional_edges is the diamond.
🎮 Playground — run the trip: each click is a new customer; sometimes the hotel sells out mid-flow.
💬 Say it in the interview: “I keep explicit state so I always know which steps are done. Each outward-facing step has a matching undo — a saga — so failures roll back cleanly. Before any risky write I pause for human approval, and everything is checkpointed so a crash resumes where it stopped.”

Q4 • Building AI vs solving the customer’s problem

Interviewer asks: An FDE doesn’t just build AI and hand it over. How do you find the real problem and deliver something people use?
🧈 Explain like I’m 5: A gadget seller shows you a shiny robot and asks if you like it. A doctor first watches you walk, asks where it hurts, then fixes the one painful thing first. An FDE is the doctor: shadow the day, find the real pain (40 min of typing per case), fix that one thing, show the hours saved — then grow.
🌍 Real world: That ~30% of AI projects die after the demo (Gartner) almost always skipped this. Winners time-study the workflow first, wrap the tools already in use (Salesforce, SAP, email), and ship one thin slice in two weeks before scaling.

🖼️ Connected diagram: discovery → thin slice → prove ROI → scale

Left-to-right = the discovery flow. The amber diamond is “did it actually save time?” If no, the dashed red arrow sends you back — you don’t scale a thing that doesn’t help.

🐍 Same as a code-review checklist

# FDE delivery loop (the graph on the left)
1. shadow      → sit with the user, time each step
2. pain        → write it in THEIR words + a number
                 e.g. "40 min x 200 cases/mo"
3. thin slice  → smallest useful fix, ~2 weeks
                 wrap existing APIs (SAP, CRM, email)
4. measure     → did real hours actually drop?
                   no  ← dashed arrow back to step 2
                   yes → prove $ to the customer
5. scale       → only after the slice earns trust

ROI pitch (40min x 200 cases, $45/hr):
   133 hrs/mo × $45 = ~$6,000/mo saved
   vs $400/mo AI cost → payback in ~3 weeks
The graph is the method. Never start at node 3 — the diamond at node 4 is what makes it a business, not a demo.
🎮 Playground — price the slice: does the ROI diamond say yes or no?
💬 Say it in the interview: “I’d spend day one shadowing the workflow and timing steps to find the real bottleneck, not the flashiest one. I’d write the problem in the customer’s words with a number attached, ship the smallest slice against the systems they already use, measure the hours saved, and only scale once that slice earns trust.”

🏆 Quick check (click to reveal)

1. A tool keeps failing. Your first two moves?

Backoff (wait longer each retry) + a timeout so you never hang. Then a safe fallback node.

2. The two RAG tests, in plain words?

Did the librarian bring the RIGHT books (recall)? Did the answer stay inside the books (faithful) instead of inventing?

3. Flight booked, hotel sold out. Smart move?

Run the compensation path: refund the flight, notify the customer, offer options. Don’t strand them.

4. Why “try it on 5 users first”?

A canary deploy — catch problems on a few people before changing it for everyone (avoid a Knight-Capital blast radius).

5. First step an FDE takes with a new customer?

Shadow the workflow and time the steps to find the real pain — before writing any AI code.

6. In a LangGraph diagram, what is a diamond?

A conditional edge (add_conditional_edges) — a yes/no route that picks the next node. The retry loop is an edge that points back to the same node.
